# Acceptance evidence and release limits

Verified locally on 14 October 2026: production build; 8 unit tests; 18 PostgreSQL integration tests; 3 browser workflows; a consistent-snapshot dump/restore comparing all 38 table counts, financial totals, 20 RLS policies/enforcement flags and document file sizes; compiled production startup, health, protected APIs and browser rendering. The dependency audit reported zero advisories. Docker/VPS deployment, wildcard HTTPS and live provider delivery were not executed in this environment.

This is an initial system built from an empty directory, not a conversion of an existing system. No old dental features could be regression-tested against an earlier implementation.

| Requested acceptance criterion      | Evidence in this implementation                                                                                                                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. Separate clinic registration     | Atomic registration and membership/default provisioning; retry returns the same unverified clinic. Integration test.                                                                                                                                         |
| 2. Clinics operate simultaneously   | Separate authenticated sessions queried concurrently. Integration test.                                                                                                                                                                                      |
| 3. Guessed patient IDs denied       | List/detail/update/create/search and FK/RLS isolation tests.                                                                                                                                                                                                 |
| 4. Attachments and exports isolated | Cross-clinic authenticated document download denied; export requires entitlement and verified patient ownership.                                                                                                                                             |
| 5. Reports scoped                   | Separate clinic collection totals verified.                                                                                                                                                                                                                  |
| 6. Doctors/staff/plans/sessions     | Backend role/limit checks, treatment acceptance, session counts and total fee invariants; workflows implemented.                                                                                                                                             |
| 7. Backend entitlements             | Concurrent doctor provisioning, storage, staff/branches/patient limits, exports and branding.                                                                                                                                                                |
| 8. Expiry/grace                     | Request-time trial/paid/cancelled checks plus lifecycle job; integration and unit tests.                                                                                                                                                                     |
| 9. Verified payments activate       | HMAC authenticated captured-payment payload bound to a server-owned invoice/order, amount and currency. Local synthetic provider event tests; live Razorpay remains unverified.                                                                              |
| 10. Duplicate webhooks harmless     | Event/payment/refund deduplication; duplicate events with different delivery IDs tested.                                                                                                                                                                     |
| 11. Separate financial ledgers      | Distinct subscription and patient tables/routes; patient collections do not create SaaS payments.                                                                                                                                                            |
| 12. Upgrade applies limits          | Audited manual upgrade enables data export. Verified paid invoices select the purchased plan.                                                                                                                                                                |
| 13. Downgrade retains data          | Plan change preserves doctors and patients. No automatic data deletion.                                                                                                                                                                                      |
| 14. Admin access controlled         | Platform credentials without membership cannot read clinic records. Exceptional read requires patient-scoped, time-limited consent and an audit entry; revoked grants fail.                                                                                  |
| 15. Backup/export correctness       | Full database dump and isolated restore compare table counts, invoice totals, RLS policies and document file sizes. Clinic and patient JSON export scope tested. Full attachment backup/restore and off-site recovery rehearsal remain operator launch work. |
| 16. Dental workflows retained       | New EMR, chart versions, treatment/session billing, installments, commissions and reporting are tested. No original repository existed to compare behavior against.                                                                                          |

Unit and integration suites run against a local PostgreSQL runtime role with NOSUPERUSER and NOBYPASSRLS. No-context RLS is verified separately from repository filters. Mutation responses are committed before delivery and generic request replay is tested for concurrent patient provisioning.

Browser verification exercises public desktop/mobile layouts and the real signup → verification → login → doctor → patient → tooth chart → treatment → session → installment → appointment flow. Final test counts/results are recorded in the handoff; screenshots and traces are local ignored artifacts under `.tools/screenshots` and `test-results`.

Not yet a commercial launch: live credentials, production HTTPS/wildcard DNS, actual payment/email sandbox delivery, recurring mandates, live provider reconciliation verification, configurable branch permissions, optional MFA, medical/legal policies, retention execution, independent security/load tests and off-site disaster recovery require further work. Customer data must not be imported until the hosting and policy gates are satisfied.
